# 쇼핑몰·D2C — 보안 점검 포트폴리오

## 고객
쇼핑몰·D2C: 회원·주문·장바구니·결제가 있는 온라인 판매. 합성 실험 대상: WhiteHat P04 결제 서비스(실제 PG 아님).

## 주요 위험 → 검증 사례

### 1. 중복 결제를 막는 장치가 오히려 정상 주문을 막는다면? (P04)
- **위험**: 멱등성 키가 고객/주문 범위로 구분되지 않으면, 공격자가 1원 결제로 키를 선점해 소유자의 50만 원 결제를 409로 막을 수 있음.
- **방치 시**: 정상 결제 실패 → 주문 손실, 고객센터 민원, 재결제 시 이중 과금 위험.
- **SUNYEDO 검증**: 1원 선점 → 50만 원 409 → 잔존 기록 amount=1 재현 (실험 P04-IDEM-01, `evidence/private/p04_before_raw.txt` P04-12..15).
- **보완**: 인증 주체(principal) 단위로 키 스코프 + 소유권 검증. 보완 후: 다른 주체 같은 키 사용 시에도 정상 결제 200 유지 (BA-06).
- **상태**: E4 완료 (Before/After 실행 검증). 합성 결제원장 — 실제 PG·웹훅은 별도 검증 필요.

### 2. 결제 키 하나로 남의 결제 내역을 본다면? (P04)
- **위험**: 결제 조회 API가 인증·소유권 검증을 안 하면 결제 키만으로 타인 금액·상태 노출.
- **SUNYEDO 검증**: 무인증 GET → 200 + amount (P04-IDOR-01, P04-10 재현).
- **보완**: 인증 + 소유자 매칭. 보완 후 무인증 401 (BA-05).

### 3. 검색창 하나로 데이터베이스가 위험해지는 이유 (OWASP SQLi)
- **위험**: 상품 검색 등 입력값이 SQL에 그대로 들어가면 UNION 인젝션으로 고객정보 열거 가능.
- **SUNYEDO 검증**: OWASP Juice Shop `/rest/products/search` UNION SQLi 재현 (교육용 앱, 2026-10-16 실행, heretic2 319s / Qwen 641s).
- **상태**: stored-result (E3). 앱은 Known vulnerable training application — 고객사 시스템이 아님.

### 4. AI 상담의 잘못된 환불 (AgentRisk, 보조)
- CS 에이전트가 권한 없이 환불·상태 변경을 실행하는 합성 실험. stored-result 검증 (E3). `LAB_USD`는 합성 금액.

## 제공 서비스
결제·주문 API 권한 매트릭스 점검 → 멱등성·소유권·입력값 검증 PoC → 수정 권고 → 재검증 보고서.
